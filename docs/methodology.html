This page is the human account of how the harness works and how it was validated. Its machine-generated counterpart is the findings site's methodology page — rebuilt by the harness every cycle, always current on constants and thresholds — available in the snapshot here and live on rk-findings. That page states what the numbers mean; this one explains why the machinery around them is built the way it is, and what was actually exercised before the run was left alone. The system itself is drawn on the architecture page; the paper trail of choices is on design decisions.

The shape of the problem

An unattended search, partly steered by a language model, produces numbers for months with nobody watching. Numbers from such a system are worth exactly as much as the guarantees around them: that the scoring rules could not drift, that the searching process could not touch its own scorer, and that a crash or a stray operator cannot silently corrupt the record. So the validation story is really three gates, engaged in order: once at container start, once inside every cycle, and continuously from the host.

The gate at container start

The container's entrypoint refuses to run science before proving its environment, in a fixed order. It writes a heartbeat immediately — the gate takes long enough that the host watchdog once killed a fresh container fourteen seconds after start, because the heartbeat file on disk predated the restart; the fix is the very first line of the entrypoint, not a longer timeout. It then probes its own mount: if /harness accepts a write, the container exits rather than run with a writable scorer. It recomputes the verifier hash and compares it to the pinned value. Finally it runs the golden and canary tests — G1 through G20 plus the K1 and K2 canaries, 55 cases at the pre-flight run — with pytest, against the harness as mounted. Any failure is exit 1 and the runner never starts.

The point of running tests at start rather than at build time: "the tests passed when the image was built" claims nothing about the harness that is mounted today. The gate re-earns the claim on every start, including every automatic restart after a kill.

Ten files, one hash

Six modules decide every score: coefficient representation, the order conditions, the verifier, the cost model, the evaluator, and the problem set. Four fixture files pin their golden values. A sha256 over those ten files, concatenated in a fixed order, is pinned in VERIFIER_HASH; the entrypoint recomputes and compares it, and every archive record stores the hash that scored it. A change to any byte of the ten is therefore loud twice over: the container refuses to start, and a record produced under a different hash would advertise the fact in its own row.

This was drilled, not assumed. Pre-flight item A3 altered one line of coeffrep.py and started the container: exit 1, "VERIFIER HASH MISMATCH — refusing to run". Restored, the same container gated green and started, the 55 golden and canary cases passing in under four seconds.

What the container cannot reach

The harness mount is read-only (:ro on the docker command line, re-checked by the entrypoint's write probe). The GitHub credential never enters the container at all: the env file the container receives is filtered on the host and drops every GITHUB_TOKEN line, the runner only ever commits into the mounted work and findings checkouts, and the host watchdog pushes those commits with the owner's own credentials every ten minutes. The Codex OAuth file is mounted read-only for the plan-billed planning calls.

The original design scoped a token instead: push rights on rk-work and rk-findings, with a 403 on rk-harness as an acceptance test. That plan failed honestly. The pre-flight scope probe showed the owner's actual token could push the verifier repo, and the earlier 403 had passed for an unrelated reason. Moving the credential out of the container entirely makes the guarantee independent of anyone's permission model — there is no token whose scope can rot. The full story is under credentials outside the container.

The test suites, tiered

The suite is organised as numbered tiers that mirror the dependency stack, cheapest and most foundational at the bottom: T1 covers fixed point, coefficient representation and cycle counting; T2 the order conditions, evaluator and verifier; T3 the archive, search and directive validation; T4 the ledger, runner and site generator; T5 the operational config and the watch view; T6 the Central-time display formatting. Together they collect a bit under a thousand parametrised cases at this snapshot, with a slow marker separating the second-scale ones.

Two kinds of test carry most of the weight. Golden tests (G-numbered) pin behaviour to fixture values written down before the build: the measured order of rk4 comes out 4.0706 from 3 fit points, the hand-counted ARMv6-M multiply sequence costs 13 cycles fast and 75 slow, and the eleven coefficient representations in the fixture reproduce bit for bit. Canary tests (K-numbered) are anti-gaming: K1 plants a candidate tuned on the search set and asserts it can earn search_only but never heldout_verified; K2 asserts that a winner in a single problem family that is worse on both aggregates stays unreplicated. The gate at container start is a selection from this same suite, so the anti-gaming properties are re-proved on the mounted code every time the container comes up.

The pre-flight, executed as a program

The pre-flight checklist (docs/REVIEW.md in the harness repo) is not a document anyone initials; scripts/preflight.py executes every machine-checkable item, prints the measured value next to each verdict, and writes the report with a sign-off block (docs/REVIEW-REPORT.md). Statuses are PASS, FAIL, MANUAL (needs the host, hardware, or a human), SKIP and INFO; the trust boundary (A), ground truth (B), anchor result (C) and falsification (K) sections gate, and a FAIL there is a nonzero exit. The full run, suite and docker drills included, was executed on 2026-08-30: every gating section green, with eight items that need the host, hardware or a human left marked MANUAL, each carrying its instructions in the report.

The drills are where the exercise paid for itself, because they act instead of asserting: A1 actually tries to write /harness from inside a running container; A3 actually tampers with a verifier file and expects the refusal; D5 deliberately feeds the optimizer the held-out set and checks the search/held-out gap collapses to zero, then returns on revert — which is what shows the gap metric measures what it claims. Three of these drills changed the system before the run started; that story is told on the architecture page.

The operational layer

Once running, the container answers to a host watchdog that polls every ten seconds and holds every kill switch outside the container. A heartbeat older than two minutes is a docker kill; a wrongful kill self-heals, because the restart policy brings the container back and the start gate re-runs. Spend over the monthly cap, or free disk under five gigabytes, is a stop that stays down. The laptop on battery is a pause, plugged back in an unpause; another foreground workload holding the CPU above 50% for thirty seconds is a pause, back under 30% an unpause. Pause is atomic, so the run resumes mid-cycle exactly where it stopped.

The run also throttles itself. Auto-stop limits (wall-clock minutes or cycle count) end the run at the next cycle boundary. The language model is asked for a fresh directive every five cycles and on every escalation, with the last directive reused in between; calls stop once Codex reports 80% of the weekly plan used; the web literature digest runs every fifty cycles and the archive interpretation every twenty-five. All of these are operational knobs in a workspace config.json edited through configure.py. Scientific thresholds are deliberately not in that file: changing them would invalidate the archive, which is why they live in the hash-pinned code instead.

One bookkeeping rule ties the layer together: everything stored — archive records, events, heartbeat, run state — is UTC, and only human-facing display converts to US Central, through one small module. The watchdog's staleness arithmetic and the archive's determinism both depend on storage never carrying a local time.

What this page does not cover

The scientific method of the search itself — the nine verifier checks in order, exact rational order conditions, equal-cycle-budget evaluation, tier assignment, the encourager ladder — is on the architecture page, and the current constants and thresholds are on the findings methodology page (snapshot, live).
